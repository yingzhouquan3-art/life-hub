# ADR-0001: 将个人账本演进为模块化个人生活平台

## 状态

Accepted

## 背景

现有产品已经是一套可用的大学生个人账本。用户希望继续使用原账本，同时逐步加入健身、饮食、睡眠、学习等个人生活能力。如果直接把新功能混入账本页面和交易数据，会让界面、数据含义和后续扩展迅速失控。

## 决策

采用一个统一平台外壳，首批包含生活总览、个人账本、健身和饮食四个模块。

- 个人账本模块继续拥有原有财务表和财务界面。
- 健身模块与饮食模块分别拥有自己的记录表和写入接口。
- 生活总览模块仅通过各模块公开的摘要接口聚合数据。
- 本地版本继续使用同一个 SQLite 文件，降低启动、备份和恢复成本；表的所有权仍按模块严格划分。
- HTTP 接口作为前端与各模块之间的边界；模块内部计算保持在后端函数中，便于独立测试。

## 后果

- 用户获得一个入口和一致导航，原账本无需迁移到另一个产品。
- 新模块可以逐个增加，而不必修改交易模型。
- 单数据库让本地使用与完整备份保持简单，但未来多人使用时需要重新评估账户隔离和权限模型。
- 生活总览依赖各模块摘要的稳定含义，因此新增模块时必须先定义自己的摘要，再接入总览。

## 考虑过的方案

### 继续在账本页面追加健身和饮食卡片

改动较小，但会让财务页面承担无关职责，导航和数据模型都会越来越难理解，因此不采用。

### 每个生活领域使用独立应用和独立数据库

隔离最强，但本地启动、备份和跨领域总览都会变复杂，当前个人单机阶段收益不足，因此暂不采用。

### 一开始建立插件系统

扩展性高，但会提前引入注册、版本和兼容机制。当前模块数量少，先采用明确的模块边界，等出现真实扩展压力后再提炼插件接口。

## 何时重新审视

- 平台需要支持多个用户或跨设备同步。
- 模块数量增长到统一发布明显困难。
- 第三方模块需要独立安装或卸载。
- 单个 SQLite 文件成为性能或权限瓶颈。
