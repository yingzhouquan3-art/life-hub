# ADR-0003: 手机端捕获与待确认条目

## 状态

Accepted

## 背景

平台已经有十一个模块，但只能在电脑上记录。健身、饮食、睡眠这三类数据天然产生在
健身房、餐桌和床上——离电脑最远的地方。只能回到电脑前补记，等于这些模块会慢慢空掉，
最后只剩账本还在用，因为只有账本有「钱」这个足够强的动机。

记账还有一层：支付宝和微信**没有面向个人的交易流水 API**。开放平台是给商户的，
个人拿不到自己账单的实时接口。市面上的「自动记账」走的都是绕路方式：
安卓通知监听、短信解析、月度账单导出。

## 决策

### 一、自动捕获不直接写成交易

支付通知里只有金额和商户，没有分类，也没有账户归属。直接入账等于系统替用户虚构事实，
违反 ADR-0001 以来「模块保存的是事实」的前提。

因此引入**待确认捕获**：单独一张表，在用户确认之前不进入余额、月度、预算和报表中的任何一项。
确认时由账本模块创建交易，捕获模块只记录对应关系——两个模块彼此仍然不知道对方存在，
跨模块编排放在 api 层。

### 二、双通道互为校验，同额且 60 秒内合并

微信支付走通知，绑定的银行卡扣款走短信，同一笔付款会被抓到两次。
合并规则是金额相同且时间相差 60 秒以内，合并后保留全部来源，
这样事后能看出哪条通道还活着。

### 三、解析放在后端

手机端只负责转发通知原文。改规则不用重新配置手机，也能对着真实原文写回归测试。
解析不出金额时不写入任何东西——**认错一个金额比认不出来危险得多**，
用户会去确认一个不存在的数字。

### 四、捕获覆盖率是通道健康度，不是记账完整度

通知监听最大的坑是**静默失败**：系统省电策略把监听服务杀掉，不报错，只是某天开始一笔都不进来。
所以要有一个数字回答「这条通道还活着吗」。它衡量的是通道，不是用户。

### 五、月度账单是权威事实，通道只是加速

平时靠捕获和手记覆盖当下，月末导入账单对账，只补差额不重复入账。
账单里状态为退款、关闭、失败的行不是实际支出，必须跳过。

### 六、非本机访问必须带令牌，且不监听 0.0.0.0

监听地址一旦不是回环，任何能到达这台机器的设备都能读到全部生活数据。
默认仍然只听 127.0.0.1；需要手机访问时绑定 Tailscale 地址。
启动脚本明确拒绝 0.0.0.0——那会把数据暴露给当前连着的任何一个网络，包括咖啡店 WiFi。

静态外壳（页面、脚本、图标）免鉴权，因为它不含数据，
而且 Service Worker 与 manifest 的请求带不上自定义头。

## 后果

- 手机上能记东西了，其余十一个模块才有持续被使用的可能。
- 自动化只降低录入成本，不污染事实：待确认条目是一道明确的闸门。
- 代价是多一步确认。这是刻意的——省掉这一步就等于让系统替用户编造分类。
- 隐私上有一个**真实且消不掉的代价**：为了让通知带上金额，
  微信的「通知显示消息详情」必须打开，于是所有聊天内容都会出现在通知栏，
  并被自动化应用读到。缓解办法是规则在手机本地严格过滤、只有匹配的才发出，
  但代价本身无法消除，用户必须知情后才决定是否启用。

## 已知未验证之处

- 通知与短信的解析规则按常见文案编写，**没有对着真机验证**。
  接入前应先用真实通知跑 `POST /api/capture/parse`。
- 账单 CSV 的列名按公开导出格式编写，同样未对真实账单验证。
  第一次导入务必先看预览，确认条数与金额。
- 纯血鸿蒙 NEXT 不运行安卓应用，也没有对等的通知监听开放能力，这条路在其上不成立。

## 考虑过的方案

### 让手机端自己做正则解析

省一次网络往返，但改规则要重配手机，而且无法回归测试。不采用。

### 自动捕获直接入账，事后再让用户改

录入成本最低，但会把系统猜的分类混进历史数据，且用户很难发现哪些是猜的。不采用。

### 监听 0.0.0.0 加令牌

实现最简单，但令牌一旦泄漏，暴露面是当前连着的整个网络。
绑定 Tailscale 地址把暴露面限制在自己的设备之间。不采用 0.0.0.0。

## 何时重新审视

- 拿到真实通知与账单原文之后，解析规则需要按实际文案重写。
- 出现第三条捕获通道（例如云闪付）时，去重规则需要重新评估。
- 电脑不再常开，需要把后端搬到常开设备时。
